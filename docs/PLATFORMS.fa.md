# سند فنی پلتفرم‌ها — دیوار و ترب

این سند «راهنمای میدانی» هر پلتفرم است: چگونه فهرست آگهی‌ها را می‌گیریم، جزئیات
کجا است، شماره تماس کجا پنهان می‌شود و ریسک‌ها چیست.

> ⚠️ **NEEDS LIVE VERIFICATION**: این سند از محیطی نوشته شده که به سرورهای
> ایران دسترسی ندارد. ساختار endpointهای هر دو پلتفرم **دوره‌ای تغییر می‌کند**.
> همه URLها در `config.py` قابل تنظیم‌اند تا اصلاح بدون تغییر کد ممکن باشد.
> اولین کار فاز ۲: ضبط پاسخ واقعی و هم‌گام‌سازی فیکسچرها با این سند.

---

## ۱. دیوار (divar.ir)

### ۱.۱ مدل داده پلتفرم
- هر آگهی یک **token** یکتا دارد → صفحه وب: `https://divar.ir/v/{token}`
- جستجو بر اساس **شهر (slug)** + **دسته‌بندی (slug)** — مثلاً:
  - تهران + خرید آپارتمان = `tehran` + `buy-apartment`
  - تهران + موبایل = `tehran` + `mobile-phones`
- سایت SPA (React) است؛ اما APIهای JSON تمیزی برای وب دارد.

### ۱.۲ endpointهای پیش‌فرض کد (قابل تغییر از config)

| مرحله | URL | خروجی |
|---|---|---|
| فهرست | `GET https://api.divar.ir/api/v1/post2/w/{city}/{category}` | JSON: `result.posts[].token` |
| جزئیات | `GET https://api.divar.ir/post/v2/web/post/{token}` | JSON کامل آگهی (`sections[]`) |

### ۱.۳ کجاها شماره تماس هست؟ (به ترتیب احتمال)
1. **widget CONTACT** در `sections` → `data.phone`
2. **متن توضیحات** آگهی (فروشندگان املاک اغلب شماره را داخل توضیح می‌نویسند)
3. **دکمه «نمایش شماره»** — در برخی آگهی‌ها شماره فقط بعد از درخواست نمایش
   ظاهر می‌شود (endpoint جدا یا رندر مرورگر) → **فاز ۲ با BrowserFetcher**
4. اصلاً نیست — بخش بزرگی از آگهی‌ها (به‌ویژه غیراملاک) **فقط چت** هستند.
   این «نقص ابزار» نیست؛ سیاست خود دیوار است. رکورد بدون شماره با
   `quality_score` پایین ذخیره می‌شود.

### ۱.۴ استراتژی پارس کد فعلی
```
1) مسیر هدفمند: walk روی JSON برای کلیدهای phone/contact_phone/…
2) متن توضیحات sections
3) Fallback: اسکن Regex کل JSON سریالی‌شده
```
یعنی حتی اگر نام widget عوض شود، شماره (اگر در پاسخ باشد) استخراج می‌شود.

### ۱.۵ ریسک‌ها
- **تغییر ساختار sections** → عنوان/دسته ممکن است جایگزین شود (شماره با Regex می‌ماند)
- **Rate-limit تهاجمی دیوار** روی API — پیشنهاد: min_delay ≥ ۲ ثانیه، batchهای کوچک
- **نبود شماره در برخی شهرها/دسته‌ها** (سیاست چت‌محور) → درصد «دارای شماره» را در گزارش ببینید
- 403/401 → احتمال بلاک IP → توقف و تغییر IP/proxy

### ۱.۶ دسته‌بندی‌های پرتقاضا (slug نمونه)
`buy-apartment` (خرید آپارتمان)، `rent-apartments` (اجاره)، `mobile-phones`،
`cars`، `laptops`، `home-appliances`، `employment` (استخدام)…
اسلاگ دقیق هر دسته از URL صفحه‌ی آن دسته در دیوار قابل کپی است.

## ۲. ترب (torob.com)

### ۲.۱ مدل داده پلتفرم
- ترب «موتور مقایسه قیمت» است: هر **محصول** یک `random_key` (prk) دارد →
  `https://torob.com/p/{prk}/`
- «فروشنده» در ترب = **فروشگاه (shop)**. لید تجاری ما = تماس فروشگاه‌های
  فعال در حوزه محصولی مشخص.
- APIهای JSON عمومی دارد (نسخه v4).

### ۲.۲ endpointهای پیش‌فرض کد

| مرحله | URL | خروجی |
|---|---|---|
| جستجو | `GET https://api.torob.com/v4/base-product/search/?q={query}&size=24&page={page}` | `results[].random_key` |
| جزئیات | `GET https://api.torob.com/v4/base-product/detail-v2/?prk={prk}` | JSON محصول + اطلاعات فروشنده |

### ۲.۳ کجاها شماره تماس هست؟
1. JSON جزئیات محصول: فیلدهای `shop_phone` / اطلاعات فروشگاه (در برخی پاسخ‌ها)
2. **صفحه فروشگاه** `https://torob.com/shop/{shop_id}/` — شماره تماس فروشگاه
   در HTML/JSON داخلی صفحه → **فاز ۲: صفحه‌ی shop + BrowserFetcher در صورت نیاز**
3. سایت فروشنده (لینک `shop_url`) → آداپتور `web` همین الان می‌تواند آن را پیمایش دهد!

### ۲.۴ جریان مرورگری کاربرگونه (فاز ۲ — پیاده‌سازی شد ✅)

علاوه بر حالت API، حالت «مرورگر واقعی» با Playwright + Chromium پیاده شده است
(`abii browse -p torob`) — دقیقاً رفتاری که کارفرما خواست:

```
ورود به torob.com → تایپ انسانیِ جستجو (حرف‌به‌حرف، تأخیر تصادفی) → اینتر
→ اسکرول طبیعی نتایج → کلیک روی محصول → کلیک روی لینک فروشنده در کارت فروشنده
→ کلیک «نمایش شماره» (شماره در سورس نیست، فقط با کلیک ظاهر می‌شود!) → کپی شماره
→ بازگشت → محصول بعدی
```

- **تست‌شده روی سرور ماک** (`examples/mock_sites/mock_torob.py`) با ۶ تست خودکار —
  از این محیط توسعه، ترب واقعی در دسترس نیست (TCP بسته است)
- **ضبط جلسه**: `--record` → ویدیو webm + اسکرین‌شات هر قدم در `sessions/`
- **رفتار انسانی**: تایپ حرف‌به‌حرف ۷۰-۱۸۰ms، مکث تصادفی بین اکشن‌ها، اسکرول
  تصادفی، `timezone=Asia/Tehran`، `locale=fa-IR`، حذف `navigator.webdriver`
- **سلکتورها** در `configs/selectors.torob.yaml` با چند کاندید برای هر فیلد —
  پارس مقاوم در برابر تغییر کلاس‌های ترب
- اجرا روی ترب واقعی: `abii browse -p torob --query "..." --headed --record`
  (از سرور داخل ایران)

### ۲.۵ موتور ناهمگام فروشگاه‌محور (حالت پرفورمنس) — پیاده‌سازی شد ✅

معماری ۳-فازی `abii torob scan`:

```
فاز ۱ (کشف):    کوئری‌ها → صفحه‌بندی search API → فهرست prk محصولات
فاز ۲ (نگاشت):  هر محصول → شناسه فروشنده‌هایش (detail + offers در صورت نیاز)
فاز ۳ (برداشت): هر فروشگاه فقط «یک بار» fetch → نام/شهر/شماره → Lead
                 ─ فروشگاه تازه‌ی‌دیده‌شده (TTL پیش‌فرض ۷ روز) رد می‌شود
```

**چرا سریع است**: فروشگاه‌ها بین محصولات مشترک‌اند؛ dedupe «قبل از fetch» یعنی
هر فروشگاه فقط یک درخواست می‌خورد. همزمانی asyncio + workerهای متعدد، ولی نرخ
کل به هر هاست با صف per-host کنترل می‌شود + کندسازی تطبیقی (با 429/5xx خودکار
آهسته‌تر می‌شود). متریک زنده: تعداد درخواست/بلاک/ری‌تری، فروشگاه/دقیقه.

**نتایج تست روی ماک** (۱۳۵ محصول، ۴۴ فروشگاه): ۱۱۸ محصول → ۳۹ فروشگاه یکتا با
۱۷۷ درخواست در ~۸ ثانیه؛ ۲۱ شماره از API، ۱۰ شماره فقط پشت دکمه «نمایش شماره»
(نیازمند گذر مرورگری)، ۸ فروشگاه واقعاً بدون شماره. اجرای دوم: صفر fetch تکراری.

**پارامترهای کلیدی**:
```bash
abii torob scan --pack digital --max-shops 100 --workers 4 --min-delay 1.2
# محافظه‌کارانه (تا ~۲۰۰۰ فروشگاه): min-delay 1.0-1.5، workers 3-5
# بسته کوئری‌ها: configs/queries.torob.yaml (digital / home / all)
```

### ۲.۶ گردش‌کار کالیبراسیون با سرور ایران (مهم!)

چون ساختار دقیق endpointهای واقعی (خصوصاً `shop/detail` و `offer-list`) فقط از
داخل ایران قابل تأیید است:

1. روی سرور ایران: `python3 scripts/probe_torob.py "لپ تاپ"` — بدون هیچ نصبی
2. فایل `torob_probe_<date>.zip` برای ما بفرستید (فقط پاسخ‌های عمومی ترب است)
3. ما: تطبیق URLها در `config.yaml` + به‌روزرسانی فیکسچرها و تست‌ها
4. سپس اجرای واقعی: `abii torob scan --pack digital --max-shops 50` روی سرور شما
5. اگر شماره فروشگاه در API نبود (مثل دکمه نمایش شماره): گذر مرورگری
   `abii browse` روی فروشگاه‌های «بدون شماره» فعال می‌شود

### ۲.۷ نقشه تکمیلی
```
browse(q) → محصولات → کارت فروشنده هر محصول → shop_id ها (یکتا)
         → صفحه shop → دکمه نمایش شماره → Lead
حالت API: offers هر محصول → فروشندههای متعدد (بیش از یک فروشنده در محصول)
```

### ۲.۵ ریسک‌ها
- فیلد `shop_phone` ممکن است در همه پاسخ‌ها نباشد → fallback صفحه shop
- تغییر نسخه API (v4 → v5) → قابل اصلاح از config
- IPهای دیتاسنتر خارج از ایران ممکن است بلاک باشند → اجرا از داخل ایران

## ۳. وب عمومی (`web`)

- ورودی: لیست URL (هر خط یک URL در فایل، یا `--url` تکرارشدنی)
- خروجی: عنوان سایت (og:title/h1/title)، توضیح متا، **همه شماره‌های متن صفحه**
  (موبایل اول)، همه ایمیل‌ها
- کاربرد: هر «سایت فروشنده» که از ترب/دیوار لینکش را گرفتید؛ یا لیست‌های
  آماده دایرکتوری کسب‌وکارها
- محدودیت: صفحاتی که شماره فقط بعد از کلیک/JS نمایش می‌دهند → فاز ۲ BrowserFetcher
