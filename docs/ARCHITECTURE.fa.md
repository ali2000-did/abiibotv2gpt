## ۱. هدف محصول — یک جمله

> رباتی که وارد پلتفرم‌های نیازمندی (دیوار، ترب، هر سایت فروشنده) می‌شود، در
> **حوزهٔ تعیین‌شده** فهرست آگهی‌ها را پیمایش می‌کند، وارد صفحهٔ هر آگهی می‌شود،
> **اطلاعات تماس (عمدتاً شماره موبایل)** و فیلدهای خواسته‌شده را استخراج می‌کند،
> سپس به سراغ مورد بعدی می‌رود؛ نتیجه: دیتابیس تمیز + خروجی اکسل/CSV بدون تکراری.

### داخل دامنه (In-scope)
- پلتفرم‌ها: **دیوار**، **ترب**، **وب عمومی** (هر لیست URL از هر سایت)
- فیلد اصلی: **شماره تماس** (موبایل/ثابت، همه فرمت‌های ایرانی و فارسی)
- فیلدهای همراه: عنوان، شهر، دسته‌بندی، قیمت، نام فروشنده، ایمیل، لینک آگهی
- پاکسازی + اعتبارسنجی + حذف تکراری + امتیاز کیفیت + خروجی CSV/XLSX/JSON

### خارج از دامنه (Out-of-scope) — فعلاً
- ارسال پیامک/تماس خودکار با لیدها (فقط *استخراج* داده، نه تماس)
- لاگین به حساب کاربری، دور زدن پرداخت یا محتوای غیرعمومی
- شبکه‌های اجتماعی (فاز ۵+ در صورت نیاز)

## ۲. اصول طراحی (ترتیب‌دار — در تعارض، بالاترین برنده است)

1. **قابلیت تست آفلاین**: کل pipeline باید بدون اینترنت روی «فیکسچر» اجرا شود. (چون محیط توسعه خارج از ایران دسترسی به این سایت‌ها را ندارد و CI هم شبکه ندارد)
2. **محترم بودن با سرور هدف (Politeness)**: rate-limit پیش‌فرض محافظه‌کارانه، retry با backoff، تلاش برای بلاک‌نکردن.
3. **API-first، مرورگر در صورت نیاز**: هرجا پلتفرم JSON می‌دهد از API می‌خوانیم (سریع‌تر، پایدارتر، ارزان‌تر)؛ Playwright فقط برای صفحات غیرقابل‌دسترس.
4. **پارس مقاوم (Resilient Parsing)**: به‌جای اتکا به یک سلکتور شکننده، «مسیر هدفمند + پیمایش بازگشتی JSON + اسکن Regex کل محتوا» — تغییر ساختار سایت، استخراج را نمی‌شکند.
5. **قابل تنظیم بودن endpointها**: URLهای دیوار/ترب در فایل config هستند نه هاردکد؛ چون ساختارشان دوره‌ای عوض می‌شود.
6. **حریم خصوصی**: داده شخصی استخراج می‌شود؛ نگهداری محلی، حذف‌پذیر، و مسئولیت حقوقی با کاربر (بخش ۳).
7. **تکامل تدریجی**: هر فاز تعریف‌شده و قابل تحویل است؛ هیچ فازی به فاز بعدی گره خورده نیست.

## ۳. محدودیت‌های حقوقی و اخلاقی ⚠️ (بخش اجباری — خوانده شود)

مسئول نقش: **مشاور حقوقی + Security Engineer**

1. **قوانین استفاده (ToS)**: شرایط استفاده دیوار و ترب، جمع‌آوری خودکار داده را
   ممنوع کرده است. استفاده از این ابزار با این پلتفرم‌ها **ریسک حقوقی و ریسک بلاک
   شدن IP** دارد. تصمیم استفاده و پیامدهایش با کاربر/کارفرماست.
2. **داده شخصی**: شماره موبایل «داده شخصی» است. در ایران مشمول قانون جرایم
   رایانه‌ای و قانون تجارت الکترونیکی است؛ استفاده تجاری از بانک شماره‌ها
   (پیامک انبوه، تماس انبوه) قواعد خاص خود را دارد. ابزار برای «استعلام و
   تماس هدفمندِ انتخابی» طراحی شده، نه اسپم.
3. **حق حذف**: هر رکورد در SQLite با یک دستور قابل حذف است؛ داده‌ها فقط محلی
   ذخیره می‌شوند و جایی آپلود نمی‌شوند.
4. **سوگیری‌های فنی پیاده‌سازی‌شده**: rate-limit پیش‌فرض ۲.۵ ثانیه + jitter،
   retry محدود، بدون تلاش برای دور زدن CAPTCHA/لاگین در فاز ۱.

> **جمع‌بندی**: ابزار خنثی است؛ کاربرد مشروع (تحلیل بازار، تماس هدفمند با
> فروشندگانی که شماره‌شان را برای تماس منتشر کرده‌اند) با کاربرد سوء، تفکیک
> مسئولیت دارد. قبل از بهره‌برداری تجاری، نظر مشاور حقوقی بگیرید.

## ۶. مدل داده

### ۶.۱ `ListingRef` — قبل از دانلود جزئیات
`source` (divar/torob/web) + `source_id` (توکن آگهی) + `url`

### ۶.۲ `Lead` — رکورد نهایی (جدول `leads` در SQLite)

| فیلد | نوع | توضیح |
|---|---|---|
| `source`, `source_id` | TEXT | کلید یکتا `(source, source_id)` |
| `url` | TEXT | لینک آگهی/محصول |
| `title` | TEXT? | عنوان آگهی |
| `category` | TEXT? | مسیر دسته‌بندی (املاک > خرید و فروش > …) |
| `city` / `district` | TEXT? | شهر / محله |
| `price` | TEXT? | قیمت (خام یا قالب‌بندی‌شده) |
| `seller_name` | TEXT? | نام فروشنده/فروشگاه |
| `phones` | TEXT (JSON array) | **نرمال‌شده به فرمت ملی**: موبایل `09xxxxxxxxx`، ثابت `021xxxxxxxx` — موبایل همیشه اول |
| `emails` | TEXT (JSON array) | |
| `description` | TEXT? | قطعه کوتاه (≤۳۰۰ کاراکتر) |
| `quality_score` | INT | ۰..۱۰۰ (وزن‌ها در §۹) |
| `status` | TEXT | `new` / `updated` / `duplicate` (نسبت به اسکن‌های قبلی) |
| `first_seen`, `last_seen` | TEXT (ISO) | رهگیری تاریخی |

جدول `scan_runs`: لاگ هر اسکن (زمان، spec، شمارنده‌ها).

## ۷. قرارداد هر ماژول (اینترفیس‌ها)

```python
# هر پلتفرمی فقط این سه متد پیاده می‌کند:
class PlatformAdapter:
    def discover(spec) -> Iterable[ListingRef]     # فهرست آگهیهای حوزه
    def fetch_detail(ref) -> JSON | HTML           # دانلود جزئیات
    def parse_detail(payload, ref) -> Lead         # استخراج ساختاریافته

# هر روش دانلود فقط این را پیاده می‌کند:
class Fetcher:
    def get(url) -> FetchResult(url, status_code, text)

# ذخیره‌سازی:
class LeadStore:
    def get(source, source_id) -> Lead | None
    def upsert(lead)          # INSERT ... ON CONFLICT UPDATE
    def all_leads() -> list[Lead]
    def record_run(spec, counts, started_at)
```

**مزیت**: افزودن پلتفرم جدید = یک فایل آداپتور با ۳ متد + یک خط در `registry.py`. تست آن با فیکسچر، بدون شبکه.

## ۸. جریان اجرای یک اسکن (Sequence)

```
CLI ──▶ ScanSpec(platform=divar, city=tehran, category=buy-apartment, max_items=50)
     ──▶ Runner.run_scan
            1. build_adapter("divar", fetcher, cfg)
            2. برای هر ref در adapter.discover(spec)  تا سقف max_items:
                 a. adapter.fetch_detail(ref)        ← rate-limit + retry + proxy/UA
                 b. adapter.parse_detail(...) → Lead  ← مسیر هدفمند + Regex fallback
                 c. normalize_lead(lead)              ← پاکسازی + امتیاز کیفیت
                 d. Deduper.classify(lead) → new/updated/duplicate
                 e. LeadStore.upsert(lead)            ← SQLite
                 f. خطا؟ → شمارنده error، ادامه به آگهی بعدی (توقف نمیخورد)
            3. export_leads(...) → CSV + XLSX + JSON
            4. report: شمارندهها + درصد داشتن شماره + میانگین کیفیت + مسیر خروجیها
            5. record_run → جدول scan_runs
```

## ۱۰. استراتژی Anti-Block (فاز ۱ و نقشه بعدی)

| لایه | فاز ۱ (✅) | فاز ۲+ |
|---|---|---|
| Rate-limit | حداقل ۲.۵s + jitter تصادفی per-host | صف زمان‌بندی‌شده (APScheduler) |
| User-Agent | چرخش ۴ UA واقعی | fingerprint کامل (Playwright) |
| Proxy | لیست قابل تنظیم در config + چرخش | health-check و حذف خودکار پروکسی سوخته |
| Retry | ۳ بار با backoff نمایی + احترام به `Retry-After` | circuit-breaker per-host |
| CAPTCHA | تلاش نمی‌کند (سیگنال ۴۰۳ → لاگ) | سرویس حل کپچا (اختیاری/مجاز?) |
| تشخیص بلاک | لاگ ۴۰۳/۴۰۱ | هشدار + توقف خودکار اسکن |

## ۱۱. استراتژی کیفیت (QA) — تعریف «درست»

- **تست واحد**: ۴۰ تست — مهم‌ترینشان `test_phone.py` با ۲۵+ حالت (فرمت‌ها، ارقام فارسی، نویسه‌های نامرئی، کاذب‌ها مثل قیمت‌ها).
- **معیار هر اسکن**: درصد رکوردهای دارای شماره، میانگین امتیاز کیفیت، شمارنده خطا.
- **هدف کیفی فاز ۲ (اندازه‌گیری روی داده واقعی)**: Precision ≥ ۹۹٪ برای شماره موبایل (هیچ شماره ساختگی/قیمت‌مانند)، Recall ≥ ۹۵٪ نسبت به مشاهده انسانی نمونه ۱۰۰تایی.
- **فیکسچر = قرارداد**: هر تغییر ساختار پلتفرم ابتدا فیکسچر را به‌روز می‌کند؛ اگر تست شکست، «آژیرِ تغییر ساختار» به صدا درآمده است.

## ۱۴. سؤالات باز برای کارفرما (پاسخ = ورودی فاز ۲)

1. **زیرساخت اجرا**: سرور داخل ایران دارید؟ (برای فاز ۲ ضروری است — از این محیط توسعه، دیوار/ترب در دسترس نیست)
2. **پروکسی**: پروکسی/مجموعه IP در اختیار دارید یا IP واحد؟
3. **حوزه اول**: کدام شهر+دسته‌بندی دیوار (و کدام دسته ترب) اولویت شروع است؟
4. **حجم هدف**: چند لید در روز/هفته؟ (تعیین‌کننده rate-limit و نیاز به صف)
5. **فیلدهای بیشتر**: غیر از شماره، چه فیلدی ارزش تجاری دارد؟ (مثلاً متراژ املاک، برند کالا، سابقه آگهی فروشنده)
